# 设备回调数据测试台：简化方案对比

> 需求基线：验证设备数据是否能传到服务器，查看每次请求的具体内容，完整保留原始数据。低访问量、低并发，四个功能清晰区分。
>
> **实施结论（2026-11-05）：已按方案二完成原生 PHP + SQLite + 原始文件版本。实际运行、配置和测试方式以项目根目录 `README.md` 为准；本文保留方案对比和决策过程。**

## 1. 所有方案共同遵守的规则

### 原始资料与原始请求都要保留

1. `C:\Users\EDY\Desktop\API服务器\原始数据` 始终只读，不修改、不追加、不移动、不删除。
2. 需要的旧脚本、文档和历史日志，仍按现有规则复制到新项目后使用。
3. 新收到的每一次回调，在解析前先保存服务器实际收到的 **原始请求体字节**，不能以格式化后的 JSON 或 `print_r` 内容代替原始数据。
4. 请求头以 PHP/Web 服务器能够获取的形式保存为 JSON，同时保存请求方法、URL、Content-Type、来源 IP 和服务器接收时间。
5. 原始请求文件只新增、不覆盖；附件和解析结果都是从原始请求生成的副本。
6. 即使解析失败，也保留记录并允许查看、复制和下载原始内容。
7. 只有原始请求保存成功后才回复设备成功；存储失败返回 5xx，避免设备误以为服务器已收到。
8. 不自动清理原始数据。以后如需保留期限或清理策略，必须由用户单独确认。

建议的新数据目录如下，全部位于新项目，不指向原始目录：

```text
storage/
├── raw/
│   ├── sms/                    # 短信接收原始请求
│   ├── status-report/          # 状态报告原始请求
│   ├── port-status/            # 端口状态原始请求
│   └── mms/                    # 彩信完整 MIME 原始请求
├── mms-attachments/            # 从原始彩信解析出的附件副本
└── app.sqlite                  # 仅方案二使用
```

每条原始记录使用独立目录：

```text
storage/raw/sms/2026/11/05/{随机ID}/
├── request.json                # 可获取的请求头与请求元数据
├── body.bin                    # 原始请求体，文本和二进制都按字节保存
└── parse-result.json           # 可选，保存解析结果或错误，不替代 body.bin
```

### 四个功能必须独立

**页面结构严格按照四个 PHP 脚本一一对应划分。** 一级导航只保留四项，菜单同时显示中文名称和脚本文件名，方便与设备配置对照；不另设综合工作台、发送任务等一级页面：

1. **短信接收 `sms_forward.php`**：对应短信接收脚本。
2. **状态报告 `sms_status_report.php`**：对应发送状态报告接收脚本，只查看报告，不提供短信发送。
3. **端口状态 `status_note.php`**：对应设备端口状态接收脚本。
4. **彩信接收 `mms_receive.php`**：对应彩信接收脚本。

每个脚本的首页都是**原始数据接收列表**，第一优先级是确认请求是否到达服务器、原始数据是否保存成功，而不是先展示解析字段。点击列表中的原始记录后，跳转到该记录的**独立解析页面**；解析页面不作为一级导航，也不在当前列表中用页签或抽屉代替。

因此页面层级固定为：四个脚本入口 → 原始数据接收列表 → 单条原始记录的独立解析页面。原始接收状态与解析状态分开：即使格式错误、解析失败，只要请求体已完整保存，仍显示“原始数据接收成功”，并允许进入解析页面查看错误和原始内容。

## 2. 方案一：纯 PHP + 文件存储

### 实现

- 四个轻量 PHP 回调入口，共用一个接收处理文件。
- 每次请求保存为一个独立目录，另外向对应功能的 `index.jsonl` 追加一行索引。
- 页面使用原生 PHP 输出 HTML，少量 CSS/JavaScript。
- 不需要 MySQL、SQLite、Redis、Node.js、Composer 或前端构建。

### 页面

采用顶部四个页签，进入后首先显示原始数据接收状态和原始记录列表；点击一条原始记录后跳转到独立解析页面，不在当前页展开解析结果。

```text
网关数据测试台
[短信接收] [状态报告] [端口状态] [彩信接收]
────────────────────────────────────────────────────────
原始数据接收列表
接收状态 | 接收时间 | 数据大小 | Content-Type | 原始内容摘要 | 操作
已保存   | ...      | ...      | ...          | ...          | 查看解析
────────────────────────────────────────────────────────
点击原始记录 → 独立解析页面 → 原始数据 / 请求头 / 解析结果
```

### 优点

- 文件最少、部署最简单，适合短期连通性测试。
- 数据目录直接复制即可备份，原始请求和程序索引一目了然。
- 即使没有数据库环境也能运行。

### 局限

- 数据多了以后，按号码、时间、TID、端口搜索会越来越慢。
- 分页、统计和筛选需要自行扫描索引文件。
- 不适合长期积累大量记录。

### 适用

只做几天或几周的小规模测试，主要查看最新请求和原始内容。

## 3. 方案二：纯 PHP + SQLite + 原始文件（推荐）

### 实现

- 四个轻量 PHP 回调入口，共用接收、解析和存储代码。
- SQLite 只保存接收索引，原始请求体独立保存为文件；打开独立解析页时从原始文件实时解析。
- 原生 PHP 输出页面，少量原生 JavaScript 完成详情切换、复制和筛选。
- 不使用 Laravel、MySQL、Redis、队列、Vue、Node.js 或后台 worker。
- 数据库只有一个 `app.sqlite` 文件，备份数据库和 `storage/raw` 即可。

### 原始列表与独立解析页的字段分工

四个原始列表默认使用共同列：**接收状态、原始记录 ID、接收时间、来源 IP、请求方法、Content-Type、数据大小、原始内容摘要、查看解析操作**。解析字段和解析结果不抢占首屏，只在点击后进入独立解析页面；打开解析页面时读取已经保存的原始文件进行解析，不修改原始文件。

| 页面 | 原始列表的摘要方式 | 点击后进入的独立解析页面 |
|---|---|---|
| 短信接收 | 原始文本或 JSON 的前若干字符，不依赖 Sender 等字段解析成功 | Sender、Receiver、Slot、SMSC、SCTS、完整正文；解析失败时仍显示完整原文 |
| 状态报告 | 原始 JSON 摘要和请求体大小 | TID、sent、failed、unsent、`sdr`/`fdr`、号码、端口、UTC 时间、失败原因 |
| 端口状态 | 原始 JSON 摘要和请求体大小 | MAC、端口、状态、SIM、运营商、信号、IMEI、IMSI、ICCID、余额、插卡/启用状态 |
| 彩信接收 | MIME 类型、请求体大小，二进制不直接展开 | 主题、发件人、收件人、正文、图片预览、附件下载、完整 MIME 原始文件下载 |

### 页面

采用左侧四项导航。每个脚本的首页只承担原始接收监控，点击原始记录后进入独立解析页面。

```text
第一层：原始数据接收列表（默认页面）
┌──────────────┬───────────────────────────────────────────────┐
│ 网关数据测试台│ sms_forward.php / 原始数据接收                │
│              ├───────────────────────────────────────────────┤
│ 短信接收      │ 最近接收时间 / 最近保存结果 / 存储目录状态     │
│ 状态报告      │ 时间范围  接收状态  [筛选]                     │
│ 端口状态      ├───────────────────────────────────────────────┤
│ 彩信接收      │ 接收状态 | 接收时间 | 大小 | 类型 | 原始摘要   │
│              │ 已保存   | ...      | ...  | ...  | [查看解析] │
└──────────────┴───────────────────────────────────────────────┘
                         │ 点击原始记录
                         ▼
第二层：独立解析页面
┌───────────────────────────────────────────────────────────────┐
│ ← 返回原始数据列表    原始记录 ID / 接收时间 / 接收状态        │
├───────────────────────────────────────────────────────────────┤
│ 原始数据（完整内容、复制、下载）                               │
│ 请求头与请求信息                                               │
│ 解析状态与解析结果；失败时显示具体错误                         │
│ 彩信在此页显示正文、附件预览和附件下载                         │
└───────────────────────────────────────────────────────────────┘
```

原始数据列表的默认列以接收信息为主，不以 Sender、TID、端口等解析字段作为主列；这些字段只在独立解析页面展示。原始文本使用等宽区域完整展示；二进制彩信不直接打印乱码，只提供文件下载，并在解析页生成可预览的附件副本。

### 优点

- 部署仍然简单，但搜索、分页、筛选和统计比文件方案可靠。
- 原始文件与结构化索引分离，既方便查询，也不会丢失原始内容。
- 适合长期反复测试，后续需要调整字段时也容易维护。
- 单用户或少量用户足够，无需为高并发增加组件。

### 局限

- 需要 PHP SQLite 扩展。
- 不适合很多用户同时写入，但当前低并发测试需求不受影响。

### 适用

持续进行设备联调，需要经常按接收时间、保存状态、记录 ID、来源 IP、Content-Type 或请求体 SHA-256 查询。**这是已选定并实现的方案。**

## 4. 方案三：PHP + MySQL + 原始文件

### 实现

- 页面和回调仍使用简单 PHP，不引入前端单页应用和异步队列。
- MySQL 保存索引与解析字段，原始请求继续保存为文件。
- 使用服务器已有 MySQL；增加简单的管理员登录和访问权限。

### 页面

采用顶部四模块 + 全宽原始数据接收表，点击原始记录后跳转到独立解析页面，不使用右侧抽屉代替解析页面，适合需要同时查看较多接收信息和多人使用的场景。

### 优点

- 方便用现有 MySQL 工具查询和备份。
- 更适合多用户、多设备或以后扩展其他测试功能。
- 数据量增长后比文件方案更容易维护。

### 局限

- 需要创建数据库、账号和备份策略。
- 对当前“验证设备是否传数据”的目标来说，初始部署和维护成本偏高。
- 多用户权限不是当前核心，容易把简单测试工具做复杂。

### 适用

服务器已有 MySQL，并且明确需要多人登录、多设备长期使用或后续扩展。

## 5. 方案对比与选择建议

| 对比项 | 方案一：文件 | 方案二：SQLite（推荐） | 方案三：MySQL |
|---|---|---|---|
| 部署复杂度 | 最低 | 低 | 中 |
| 外部服务 | 无 | 无 | 需要 MySQL |
| 原始请求完整保存 | 是 | 是 | 是 |
| 搜索、分页、筛选 | 基础 | 方便 | 方便 |
| 长期反复测试 | 一般 | 合适 | 合适 |
| 多人与后续扩展 | 较弱 | 一般 | 较好 |
| 当前需求匹配度 | 短期测试高 | **最高** | 略显复杂 |

选择建议：

- **只验证一次或短期联调：方案一。**
- **需要持续测试并方便查历史：方案二。**
- **已经有 MySQL、需要多人使用：方案三。**

## 6. 推荐方案的最小功能清单

若选择方案二，第一版只做以下功能：

- 四个独立回调地址和四个独立页面。
- 保存原始请求体、可获取请求头、来源 IP、接收时间和解析错误。
- 各页面首先展示原始接收状态、原始记录、接收时间、请求类型、大小和分页筛选。
- 点击原始记录进入独立解析页面，页面内依次展示原始数据、请求信息和解析结果。
- 原始文本复制、单条原始文件下载。
- 彩信正文与附件预览，完整 MIME 原始文件下载。
- 简单的存储状态显示，不做复杂统计仪表盘。
- 一个管理员密码或 Web 服务器 Basic Auth，避免测试数据公开。
- 可选历史日志导入必须另行复制来源文件，先 dry-run，默认不导入。

第一版不做：短信发送、用户角色体系、Redis、队列、WebSocket、自动刷新高频轮询、报表图表、远程设备控制、自动删除原始数据。

## 7. 统一视觉方向

沿用“信号机架”的冷调硬件风格，但进一步克制：

- 机箱雾灰背景、白色工作区、载波青作为唯一主操作色。
- 四个功能通过明确文字、独立导航和不同字段区分，不依赖四种颜色区分。
- 无宣传式首页、无大 KPI 卡片、无渐变和无意义动效。
- 页面首屏直接显示“最近是否收到数据”和记录列表。
- 解析失败使用文字与告警色，同时仍可打开原始数据。
- 桌面端列表 + 详情；手机端列表优先，点击进入独立详情页。
- 所有原始数据区域支持横向滚动，长文本不破坏页面布局。

最终技术方案选定后，再将本文件中的对应方案转为正式开发清单，其余方案保留作决策记录。
